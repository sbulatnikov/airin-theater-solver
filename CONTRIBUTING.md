# Участие в разработке

Спасибо за интерес к «Суфлёру». Этот документ описывает, как подготовить изменение, которое можно безопасно проверить и принять.

## Перед началом

1. Проверьте существующие issues и pull requests, чтобы не дублировать работу.
2. Для заметного изменения поведения сначала создайте issue с примером из игры.
3. Не объединяйте несвязанные исправления в один патч.

## Подготовка окружения

```bash
git clone <your-fork-url>
cd AirinPlaySolver
corepack enable
pnpm install --frozen-lockfile
pnpm test
```

Поддерживаются Windows, Linux и macOS. Не добавляйте платформенные команды в общие npm-скрипты без кроссплатформенной альтернативы.

## Ветка

Создавайте ветку от актуального `main`:

```bash
git switch main
git pull --ff-only
git switch -c fix/short-description
```

Допустимые пользовательские префиксы: `fix/`, `feat/`, `hotfix/`, `docs/` и `ci/`. Ветки `dependabot/*` создаются
ботом, а `rc/*` — только maintainer при подготовке релиза.

## Границы версий

- изменение только v1 должно находиться в `apps/v1` или `core/v1`;
- изменение только v2 — в `apps/v2` или `core/v2`;
- общее правило игры меняется в `core/shared` и требует тестов обоих поколений;
- визуальный общий компонент меняется в `packages/ui` и проверяется в обеих сборках;
- приложение не должно импортировать движок другого поколения.

Не редактируйте и не коммитьте `.build/` или `dist/`.

## Изменение механики

Для исправления расчёта приложите доказательство: минимальную последовательность реплик, ожидаемые промежуточные цветовые очки и восторг. Добавьте изолированный тест правила; лог целой партии или debug-снепшот можно приложить как дополнительное подтверждение, но тест не должен зависеть только от конкретной сыгранной партии.

Не меняйте подтверждённое правило только ради улучшения прогнозируемого результата стратегии.

## Проверка

Перед отправкой обязательно выполните:

```bash
pnpm test
```

Biome должен завершаться без замечаний. Для локального автоматического исправления используйте `pnpm check:write`; не добавляйте параллельную конфигурацию ESLint или Prettier.

Для изменения интерфейса дополнительно откройте обе собранные страницы из `dist/v1/index.html` и `dist/v2/index.html` хотя бы в одном Chromium-браузере.

## Версии

Не повышайте версию для чернового патча без договорённости с владельцем. Если bump входит в задачу, используйте:

```bash
pnpm version:set v1 1.9.0
pnpm version:set v2 2.3.0
```

Правила выбора MAJOR/MINOR/PATCH описаны в `docs/versioning.md`.

## Pull request

Выберите шаблон, соответствующий префиксу ветки: `feat.md`, `fix.md`, `hotfix.md`, `ci.md` или `rc.md`. GitHub не
выбирает один из нескольких PR-шаблонов по имени ветки автоматически, поэтому при работе через CLI передайте файл явно:

```bash
gh pr create --base main --template .github/PULL_REQUEST_TEMPLATE/feat.md
```

В Web UI шаблон можно выбрать параметром `template`, например `?template=feat.md`. Dependabot формирует описание PR
самостоятельно. Для `docs/*` отдельный шаблон пока не используется.

В описании укажите:

- проблему и ожидаемое поведение;
- затронутое поколение;
- способ ручной проверки;
- добавленные или изменённые тесты;
- debug-снепшот или лог партии для исправлений механики.
- краткую пользовательскую запись в `CHANGELOG.md` под `## Unreleased`; номер будущей версии указывать не нужно.

Сохраняйте commits небольшими и осмысленными. Не переписывайте историю после начала review без необходимости.

Рабочий pull request открывается в `main`, но approval не гарантирует ближайший релиз. Maintainer сам выбирает PR и
добавляет его в единственную активную RC-ветку командой `pnpm rc:add <PR>`; один исходный PR становится одним
squash-коммитом с сохранёнными номером и contributor. RC PR вливается через rebase merge после Code Freeze. Только
`hotfix/*` может пройти отдельным squash PR непосредственно в `main` и повысить исключительно patch. Прямой push в
`main` запрещён. Полная схема описана в [ветках](docs/branches.md) и [релизах](docs/releases.md).

## Передача `.patch` без pull request

Создать патч из commits относительно `main`:

```bash
git fetch origin
git format-patch origin/main --stdout > solver-change.patch
```

Проверить патч перед применением:

```bash
git apply --check solver-change.patch
```

Применить обычный diff-патч:

```bash
git apply solver-change.patch
```

Если патч создан через `git format-patch` и нужно сохранить автора и commits, используйте `git am solver-change.patch`.
