# Релизы репозитория

Репозиторий выпускается целиком и использует календарную схему JetBrains `YYYY.R[.B]`:

- `YYYY` — год выпуска;
- `R` — последовательный функциональный релиз года, начиная с 1;
- `B` — необязательный номер hotfix.

Например, `2026.1` — первый функциональный релиз 2026 года, `2026.1.1` — его первый hotfix, `2026.2` — следующий функциональный релиз. Версии приложений и движков v1/v2 остаются независимыми SemVer и фиксируются внутри общего релиза.

## Обычная разработка

1. Разработка ведётся в ветках `feat/*` и `fix/*`. Внутри рабочей ветки разрешена последовательность небольших осмысленных commits.
2. Рабочая ветка открывает pull request в `main` и получает обязательный review, но не вливается туда напрямую.
3. Maintainer вручную переносит каждую одобренную ветку в активный RC отдельным squash-коммитом. Один commit в RC соответствует одному логическому изменению и исходному PR.
4. После переноса исходный PR закрывается вручную со ссылкой на интеграционный commit.

Прямой push в `main` запрещён ruleset. Функциональные изменения попадают туда только через RC PR.

## Release candidate

Кандидат строится от последней стабильной версии. Если текущий релиз — `2026.1`, первая ветка называется `rc/2026.1-rc.1`, а будущий стабильный релиз — `2026.2`. Если текущий релиз — `2026.1.3`, кандидат `rc/2026.1.3-rc.1` всё равно готовит `2026.2`: функциональный выпуск повышает minor и сбрасывает patch.

1. Создайте ветку кандидата от актуального `main` и сразу откройте из неё PR в `main`:

```bash
git switch main
git pull --ff-only
git switch -c rc/2026.1-rc.1
pnpm release:set 2026.2
```

2. Обновите затронутые SemVer компонентов через `pnpm version:set`, отредактируйте `CHANGES.md` для будущей стабильной версии и добавляйте одобренные изменения squash-коммитами.
3. Номер кандидата не меняется от push: в одну ветку можно добавлять фичи и исправления сколько угодно. Одновременно открыт только один RC PR.
4. Если кандидат решено отбросить, закройте его PR и создайте новую ветку с очередным номером, например `rc/2026.1-rc.2`. Старый номер повторно не используется.

## Freeze

После успешной сборки RC последняя job `Freeze` ожидает ручного одобрения в GitHub Environment `release-freeze`. Новый push отменяет ожидающую job и запускает pipeline заново, поэтому замораживается только последний зелёный commit.

После одобрения `Freeze`:

1. проверяет имя ветки, общий номер будущего релиза, наличие единственного открытого RC PR и происхождение от текущего стабильного тега;
2. делает RC-ветку read-only через GitHub Branch Protection;
3. создаёт неизменяемый аннотированный тег без префикса ветки, например `2026.1-rc.1`;
4. публикует prerelease с автономными HTML v1/v2, общим архивом, `CHANGES.md` и `SHA256SUMS.txt`.

После Freeze новые commits в эту ветку запрещены, включая push администратора. Если нужны изменения, создаётся новый кандидат.

Для ручного барьера Environment должен требовать reviewer. В его secret `REPOSITORY_ADMIN_TOKEN` хранится fine-grained token с правом Repository administration: write; он используется только для включения `lock_branch`. Обычный `GITHUB_TOKEN` не имеет права менять Branch Protection.

## Стабильный функциональный релиз

Замороженный RC PR вливается в `main` через rebase merge. Squash всего RC PR использовать нельзя: отдельные squash-коммиты исходных изменений должны сохраниться. Workflow `Finalize repository release` проверяет RC-тег и автоматически создаёт следующий стабильный тег (`2026.1-rc.1` → `2026.2`) на итоговом commit в `main`.

Стабильный GitHub Release получает текст из `CHANGES.md` и тот же набор артефактов. Сгенерированные `dist` и HTML не хранятся в Git.

## Hotfix

Срочное исправление не проходит через RC:

1. создайте `hotfix/*` от актуального `main`;
2. повысьте только patch общей версии, например `pnpm release:set 2026.1.1`;
3. обновите тесты и `CHANGES.md`, откройте PR непосредственно в `main`;
4. после approval и зелёного `build` выполните squash merge или rebase merge.

После merge workflow проверит, что относительно последнего стабильного тега увеличился только patch (`2026.1` → `2026.1.1`, `2026.1.1` → `2026.1.2`), затем автоматически создаст стабильный тег и Release. Из `hotfix/*` нельзя выпускать следующий minor.

## Правила GitHub

Импортируемые конфигурации находятся в `.github/rulesets`:

- `main.json` требует PR, один approval, разрешение review threads, успешный check `build` и линейную историю; прямой и force push запрещены;
- `tags.json` запрещает перенос и удаление любого уже созданного тега, но не мешает создавать новые;
- RC остаётся изменяемым до ручного Freeze, после чего отдельная Branch Protection блокирует эту точную ветку.

В настройках репозитория разрешены squash merge и rebase merge, merge commits отключены. Текст `CHANGES.md` редактируется вручную ради ясной и аккуратной подачи; Git-история не используется как готовое описание релиза.
