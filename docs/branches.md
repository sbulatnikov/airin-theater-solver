# Ветки и Pull Requests

`main` всегда соответствует последнему коду, принятому для production. Прямой push в `main` запрещён: любое изменение
попадает туда только через Pull Request с обязательными проверками и approval.

## Рабочие ветки

| Шаблон | Назначение | Путь в `main` |
|---|---|---|
| `feat/*` | новая возможность | выбранный squash-коммит в RC |
| `fix/*` | обычное исправление | выбранный squash-коммит в RC |
| `dependabot/*` | обновление зависимости | выбранный squash-коммит в RC |
| `hotfix/*` | срочное production-исправление | отдельный squash PR напрямую в `main` |
| `docs/*` | только документация | отдельный squash PR напрямую в `main`, без релиза приложения |
| `ci/*` | только CI/CD и repository automation | отдельный squash PR напрямую в `main`, без релиза приложения |
| `rc/*` | вручную выбранный состав функционального релиза | единый RC PR в `main` через rebase merge |

Рабочий PR направляется в `main`, но approval означает только готовность изменения. Он не означает автоматическое
включение в ближайший релиз. До появления RC одновременно могут ожидать десятки готовых PR.

Каждый рабочий PR обязан добавить краткое пользовательское описание в `## Unreleased` файла `CHANGELOG.md`. Номер
будущего релиза указывать нельзя: он ещё неизвестен.

## Документация и CI

Ветка `docs/*` может изменять только документацию. После проверок и approval её PR принимается напрямую в `main` и не
создаёт новую версию, тег, GitHub Release, артефакты или deployment приложения. Такой PR не участвует в RC и не обязан
добавлять запись в пользовательский `CHANGELOG.md`.

Ветка `ci/*` предназначена только для workflow, repository automation и связанных с ними скриптов и конфигурации.
После проверок и approval её PR также принимается напрямую в `main`, минуя RC, и сам по себе не выпускает новую версию
приложения. Изменения продукта, UI и движков в `docs/*` и `ci/*` запрещены.

## Создание RC

Maintainer создаёт единственную активную RC-ветку от опубликованного `origin/main`:

```bash
pnpm rc:create
```

Команда проверяет чистое рабочее дерево, обновляет `origin/main` и теги, запрещает второй активный RC PR, выбирает
следующий свободный номер кандидата и создаёт локальную ветку, например `rc/2026.1-rc.1`. Ветка изначально полностью
совпадает с `main`; команда ничего не коммитит и не пушит.

Maintainer сам выбирает готовые PR:

```bash
pnpm rc:add 17
pnpm rc:add 24
```

`rc:add` принимает только открытый недрафтовый PR в `main`, требует изменение `CHANGELOG.md`, fetch-ит его head и
создаёт один squash-коммит. Subject заканчивается номером исходного PR, а автором коммита становится GitHub contributor:

```text
feat(ui): add tutorial (#17)

Source-PR: https://github.com/sbulatnikov/airin-theater-solver/pull/17
Source-Contributor: @contributor
```

При конфликте инструмент останавливается: maintainer разрешает конфликт и сохраняет тот же суффикс `(#17)` в ручном
коммите. Невыбранные PR и их записи `Unreleased` в RC не попадают.

## Подготовка версии

Когда состав кандидата закончен, версия назначается всему набору сразу:

```bash
pnpm release:prepare 2026.2
git add CHANGELOG.md README.md package.json
git commit -m "chore(release): prepare 2026.2" -m "Release-Notes: skip"
```

Команда переносит содержимое `Unreleased` в датированный раздел `2026.2`, открывает новый пустой `Unreleased` и
синхронизирует версию репозитория в `package.json` и README. Trailer `Release-Notes: skip` исключает технический commit
из пользовательского Change Log GitHub Release.

После этого RC пушится и открывает PR в `main`. RC PR нельзя squash-ить: используется rebase merge, сохраняющий по
одному коммиту на каждый выбранный исходный PR.

## После релиза

После принятия RC PR workflow создаёт стабильный тег, GitHub Release, артефакты и деплой Pages. Включённые исходные
PR закрываются maintainer как выпущенные; остальные остаются открытыми и могут быть выбраны в следующий RC.
