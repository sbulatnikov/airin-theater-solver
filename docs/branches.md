# Ветки и Pull Requests

`main` содержит последний принятый код. Обычный пользователь не может отправить туда commit напрямую: любое изменение
проходит Pull Request и обязательные проверки. Единственное исключение — технический release-коммит, отправленный
workflow через отдельный write deploy key после принятого продуктового PR.

## Рабочие ветки

| Шаблон | Назначение | Путь в `main` |
|---|---|---|
| `feat/*` | новая возможность | squash PR, автоматический функциональный релиз |
| `fix/*` | обычное исправление | squash PR, автоматический функциональный релиз |
| `dependabot/*` | обновление зависимости | squash PR, автоматический функциональный релиз |
| `hotfix/*` | срочное production-исправление | squash PR, автоматический patch-релиз |
| `docs/*` | только документация | squash PR без релиза приложения |
| `ci/*` | CI/CD и repository automation | squash PR без релиза приложения |
| `rc/*` | опциональный заранее собранный кандидат | rebase PR после Code Freeze |

Каждый продуктовый PR добавляет краткое пользовательское описание в `## Unreleased` файла `CHANGELOG.md`. Номер
будущего релиза в рабочей ветке не задаётся: его вычисляет pipeline после merge.

## Автоматический выпуск из `main`

Workflow `Release main` рассматривает весь диапазон от последнего стабильного тега до актуального `main`, а не только
последний commit. Поэтому временный сбой или промежуточный `ci/*` commit не теряет ещё не выпущенное изменение.

1. Pipeline связывает каждый пользовательский commit с исходным Pull Request.
2. Только `docs/*` и `ci/*` дают результат `none` и не создают app release.
3. `hotfix/*` без других продуктовых веток выбирает следующий patch; остальные продуктовые ветки — следующий
   функциональный номер.
4. Если версия ещё не подготовлена, GitHub Actions датирует `Unreleased`, обновляет `package.json` и README и создаёт
   линейный commit `chore(release): prepare <version>` с `[skip ci]` и trailer `Release-Notes: skip`. Skip-директива
   не создаёт второй workflow run от технического push.
5. Тег ставится на release-коммит, после чего тот же run собирает GitHub Release и публикует Pages.

Ruleset разрешает прямое обновление `main` только отдельному release deploy key. Его закрытая часть хранится в Actions
secret `RELEASE_DEPLOY_KEY`, подключается лишь на время job создания тега и удаляется checkout-action в конце job.
Все остальные акторы, включая maintainer и обычный `GITHUB_TOKEN`, по-прежнему обязаны использовать PR; force push и
удаление запрещены. Устаревший параллельный run не перезаписывает новый `main`: его выпуск безопасно пропускается и
обрабатывается следующим run.

## Документация и CI

Ветка `docs/*` может изменять только документацию. Для неё лёгкий job проверяет границы diff. Ветка `ci/*`
предназначена только для workflow, repository automation и связанных скриптов. Если после последнего стабильного тега
нет ожидающего продуктового изменения, merge таких PR не меняет версию, тег, Release или deployment приложения.

## Опциональный Release Candidate

RC остаётся доступен для выпуска нескольких PR одной заранее проверенной группой. Пока выбранные рабочие PR остаются
открытыми, maintainer создаёт кандидата от полностью выпущенного `main`:

```bash
pnpm rc:create
pnpm rc:add 17
pnpm rc:add 24
```

`rc:add` переносит каждый выбранный PR одним squash-коммитом с номером и contributor. Когда состав закончен, версия
назначается всей группе:

```bash
pnpm release:prepare 2026.3
git add CHANGELOG.md README.md package.json
git commit -m "chore(release): prepare 2026.3" -m "Release-Notes: skip"
```

RC PR вливается через rebase merge после Code Freeze. Pipeline видит уже подготовленную версию, валидирует её и не
создаёт второй release-коммит.

## После релиза

Стабильный тег, GitHub Release, архив и Pages соответствуют одному release-коммиту. Технический commit не попадает в
пользовательский Change Log, а новая секция `Unreleased` остаётся готовой для следующего PR.
